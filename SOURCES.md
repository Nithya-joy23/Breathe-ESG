## 1. SAP Fuel & Procurement (Scope 1)

### Real-World SAP Export Formats

I researched four ways to extract data from SAP:

**Option A: IDoc (Intermediate Document)**
- Format: Proprietary EDI format
- Requires: Live S/4HANA instance, RFC connectivity, EDI subsystem configured
- Realistic? No. Requires enterprise integration infrastructure that doesn't exist for a prototype.

**Option B: OData Service**
- Format: REST-like HTTP API
- Requires: S/4HANA instance running OData layer, OAuth credentials, live connectivity
- Realistic? No. Requires live SAP infrastructure and credentials.

**Option C: BAPI (Business Application Programming Interface)**
- Format: Not a file format; requires RFC calls into SAP system
- Requires: Live SAP system, Jython/Python RFC library (pynwrfc), connection details
- Realistic? No. Only available for live systems, not for prototype data.

**Option D: Flat File CSV from SAP GUI (Chosen)**
- Format: CSV export from SAP transaction MB51 or MB52 (Material Document list)
- Realistic? Yes. Sustainability teams typically receive this because:
  - No IT infrastructure required
  - Generated by business users via SAP GUI â†’ download â†’ email
  - Most common format in actual sustainability reporting workflows
  - Matches how real firms handle data: "sustainability@company.com gets a CSV from materials team"

### What Real SAP Material Movements Look Like

From actual SAP systems (transaction MB51 export):

```
Buchungsdatum,Werk,Material,Menge,Meins,Bewegungsart,Kostenstelle
01.03.2024,1000,DIESEL-HSD-001,500,L,201,CC-MAINT
15.03.2024,1000,DIESEL-HSD-001,320,L,201,CC-OPS
02.03.2024,2000,NATGAS-COM-002,1200,M3,201,CC-HEAT
10.03.2024,1000,DIESEL-HSD-001,200,GAL,101,CC-STORE
05.03.2024,3000,UNKN-FUEL-999,,L,201,CC-FACILITY
```

**Key observations:**
- Column headers are in German (Buchungsdatum = posting date, Werk = plant, Menge = quantity, Meins = unit of measure)
- Movement types: `201` = material consumed, `101` = goods receipt (not consumption)
- Movement type 101 rows should be skipped (fuel arriving, not burned)
- Units vary: L (litres), M3 (cubic metres), GAL (US gallons), KL (kilolitres)
- Material codes follow patterns: `DIESEL-HSD-001`, `NATGAS-COM-002` (prefix indicates fuel type)
- Some rows have missing quantities (data quality issue in real systems)
- Dates are in DD.MM.YYYY format (German locale)

### Our Approach

**Chosen format**: Flat CSV export from SAP transaction MB51

**Why**:
- Realistic: This is what sustainability teams actually receive
- Testable without infrastructure: We can fabricate realistic data
- Data quality issues present: Empty quantities, unit mismatches, inconsistent dates
- Defensible: "This is the lowest common denominator of what every SAP customer has"

**What we handle**:
- German column headers (rename to English: Buchungsdatum â†’ posting_date)
- Multiple date formats (DD.MM.YYYY, YYYY-MM-DD, YYYY/MM/DD)
- Unit conversion: L, LTR, KL, M3, GAL â†’ standardized litres
- Movement type filtering: Only type 201 (consumed), skip 101 (received)
- Material code prefix matching: `DIESEL*` â†’ 2.68 kg CO2e/L, `NATGAS*` â†’ 2.04 kg CO2e/mÂ³
- Missing quantities: Marked as parse error, row skipped

### What Breaks in Real Deployment

1. **Plant code lookup table is hardcoded** â€” Real deployment needs per-client mapping (Plant 1000 â†’ Chennai HQ, Plant 2000 â†’ Mumbai, etc.)
2. **Locale-specific dates** â€” If client's SAP uses a different locale, date format changes. YYYY-MM-DD breaks DD.MM.YYYY parser.
3. **Material codes are client-specific** â€” Our material-to-emission-factor map won't apply to a new client. Would need a lookup table.
4. **Movement types might vary** â€” Different SAP configurations use different movement type codes.

### Sample Data

Our `sap_export.csv` includes:
- 25 rows of realistic data
- Consumption rows with mixed fuel/material codes
- Movement type 101 (goods receipt, should skip): 1 row
- Missing quantity value: 1 row (to test error handling)
- Multiple units: L, KL, KG, M3 (to test conversion logic)
- Mixed date formats: DD.MM.YYYY and YYYY/MM/DD (to test parsing)

## 2. Utility Electricity (Scope 2)

### Real-World Utility Data Sources

I researched three ways to get utility consumption data:

**Option A: PDF Bills**
- Format: PDF invoice from utility company
- Requires: OCR (Optical Character Recognition), document parsing
- Problem: OCR is a document processing problem, not an emissions problem. Scope creep.
- Realistic? Yes (most utilities send PDFs). But implementationally messy.

**Option B: Utility API**
- Examples: EnerNOC, Enel X, Sense, etc.
- Requires: OAuth credentials tied to customer accounts, live API key
- Problem: Cannot obtain credentials for prototype; would need to mock.
- Realistic? Yes at scale. No for prototype.

**Option C: Portal CSV Export (Chosen)**
- Format: CSV downloaded from utility portal by facilities manager
- Process: Facility manager logs into utility website â†’ downloads monthly usage report â†’ emails CSV to sustainability team
- Realistic? Yes. This is what actually happens at scale.

### What Real Utility Data Looks Like

From actual utility portals (India CEA electricity data):

```
meter_id,account_number,period_start,period_end,kwh_consumed,peak_kw,tariff_code
MTR-45678,ACC-00123,2024-01-05,2024-02-08,12450,48.3,LT-IND
MTR-45678,ACC-00123,2024-02-08,2024-03-11,11820,45.1,LT-IND
MTR-91011,ACC-00124,2024-01-12,2024-02-14,8320,31.7,LT-COM
```

**Key observations:**
- Billing periods do NOT align to calendar months (Jan 5 â€“ Feb 8, not "January")
- Each row is a billing cycle, not a day or month
- `kwh_consumed` is total consumption in the billing period
- `peak_kw` is demand charge (peak usage), not needed for CO2e but useful for anomaly detection
- Tariff codes indicate customer type: `LT-IND` (Low Tension Industrial), `LT-COM` (Low Tension Commercial)
- Account numbers tie multiple meters to one billing account
- Periods can overlap or have gaps (data quality varies by utility)

### Our Approach

**Chosen format**: Portal CSV export

**Why**:
- Realistic: Facilities teams do this today
- Testable: Can fabricate real-looking data without OAuth setup
- Standard columns: meter_id, period_start, period_end, kwh_consumed
- Defensible: "This is the lowest friction way a client can share utility data"

**What we handle**:
- Non-calendar billing periods (Jan 5 â€“ Feb 8): Store both start AND end dates, never guess a month
- Missing kWh values: Mark as parse error
- Negative kWh (net metering, e.g., solar export): Flag as anomaly, still calculate (negative CO2e is technically correct)
- Tariff codes: Store but don't enforce (future: could vary emission factors by tariff)

**Emission factor**: 0.233 kg CO2e/kWh (India CEA 2023 average)

### What Breaks in Real Deployment

1. **Grid region emission factors vary** â€” India uses 0.233, UK uses 0.207, US EPA eGRID varies by region (0.4â€“0.6 kg CO2e/kWh depending on grid). Would need a `grid_region` field on data source configuration.
2. **Net metering edge case** â€” Customers with solar send power back to grid (negative consumption). Our calculation produces negative CO2e, which is correct but confusing. Analyst needs UI warning.
3. **Tariff structure not modeled** â€” Some utilities charge differently for peak vs off-peak, but we only have one consumption figure. Would need detailed interval data (15-min granularity) for accuracy.

### Sample Data

Our `utility_export.csv` includes:
- 12 rows across four meters and several billing periods
- Billing periods that don't align to calendar months (to test period handling)
- One row with missing kWh (to test error handling)
- Two different tariff codes: HT-1 (High Tension Industrial), LT-2 (Low Tension Commercial)

## 3. Corporate Travel (Scope 3)

### Real-World Travel Data Sources

I researched two options:

**Option A: Direct Concur/Navan API**
- Format: REST API (JSON)
- Requires: OAuth 2.0 enterprise credentials, no public sandbox
- Problem: Cannot provision credentials for prototype. Would need to mock.
- Realistic? Yes at enterprise scale. No for prototype.

**Option B: Concur CSV Export (Chosen)**
- Format: CSV download from Concur portal by travel manager
- Process: Travel manager runs report in Concur portal â†’ "Trip Summary" export â†’ emails CSV to sustainability team
- Realistic? Yes. This is what actual travel programs do.

### What Real Travel Data Looks Like

From Concur/Navan travel reports:

```
trip_id,employee_id,travel_date,mode,cabin_class,origin,destination,hotel_nights,hotel_name
TRP-10021,EMP-00441,2024-02-14,FLIGHT,ECONOMY,BOM,LHR,0,
TRP-10022,EMP-00441,2024-02-21,FLIGHT,BUSINESS,LHR,BOM,0,
TRP-10023,EMP-00882,2024-02-18,FLIGHT,ECONOMY,DEL,BLR,0,
TRP-10024,EMP-00882,2024-02-18,HOTEL,,BLR,,2,Marriott Bangalore
```

**Key observations:**
- Flights don't include pre-calculated distance; only origin/destination airport codes (IATA codes: BOM=Bombay, LHR=London, DEL=Delhi, BLR=Bangalore)
- We must resolve IATA codes to lat/lon, then calculate distance using Haversine formula
- Cabin class (ECONOMY, BUSINESS, PREMIUM) determines emission factor multiplier (BUSINESS = 2.9Ã— ECONOMY)
- Hotel stays are separate rows with `hotel_nights` and `hotel_name`
- Ground transport data quality varies; car rows can be calculated, unsupported modes are flagged
- Employee ID ties to corporate badge; can later join to headcount for normalized metrics

### Our Approach

**Chosen format**: Concur CSV export with IATA airport codes

**Why**:
- Realistic: Travel programs export this every month
- Defensible: "Most travel data lives in Concur or Navan; their CSV export is the standard"
- Calculable: IATA codes have public mapping (airport databases)
- Auditable: Trip IDs tie back to expense reports

**What we handle**:
- IATA airport code resolution: BOM â†’ coordinates (28.5561Â°N, 77.1Â°E)
- Haversine distance calculation: Great-circle distance between origin and destination
- Cabin class multiplier: ECONOMY = 0.255 kg CO2e/km, BUSINESS = 0.739 kg CO2e/km (2.9Ã— premium)
- Hotel stays: 20 kg CO2e per night (simplified flat rate)
- Invalid airport codes: Create flagged records for analyst review
- Unsupported modes or missing required fields: Flag or fail the row depending on whether a reviewable record can be created

**Emission factors**:
- Flight: 0.255 kg CO2e/km (DEFRA 2024 long-haul economy average)
- Business class: 0.255 Ã— 2.9 = 0.739 kg CO2e/km
- Hotel: 20.8 kg CO2e/night (MoEFCC 2023 estimate)
- Ground transport car: 0.171 kg CO2e/km (MoEFCC 2023)

### What Breaks in Real Deployment

1. **IATA lookup table covers ~10,000 airports; ours covers 6** â€” Production would use OurAirports.org API or similar
2. **Haversine underestimates by 8â€“12%** â€” Real flight routing adds distance. To fix: Use GCD distance + 10% uplift, or integrate with flight routing API
3. **Hotel emission factors are location-agnostic** â€” London hotel and Bangalore hotel have different grid intensities. Production needs geolocation-aware hotel factors
4. **Ground transport coverage is limited** - Car distance rows are supported, but train/taxi/bus need better factors and source data.
